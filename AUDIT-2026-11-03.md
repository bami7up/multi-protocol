## 3. P1 — исправить в первую очередь

### A-1. Multi-node перезаписывает чужую ноду

**Как воспроизводится.** В ручном/расширенном режиме по умолчанию `PREFIX=usa`
(`remnanode-setup.sh:46`), а хосты строятся как `usa1.<домен>` и `usa3.<домен>`
(`2810-2812`). Для двух нод на одном домене с одинаковым префиксом:

```text
node1 name = node-usa1.example.com
node1 profile = multi-usa1-example-com
node1 tag = USA1
```

Это подтверждено запуском извлечённых `panel_node_name`/`panel_profile_name`/`panel_node_tag`.
Далее:

* `panel_find_node_by_address` (`1474-1489`) ищет не только по address, но и по имени:
  `select(.name == $n)`. У второй ноды address другой, но имя совпадает → находится **первая**
  нода, и `panel_upsert_node` делает `PATCH`, меняя ей address/port/profile на вторую ноду.
* `panel_find_profile_by_name` (`1447-1458`) находит профиль первой ноды по имени, и PATCH
  заменяет его конфиг (включая сертификаты/пути второй ноды).
* `panel_find_host_by_remark` (`1491-1501`) находит хосты первой ноды по remark
  `"VLESS Vision usa"` и переписывает их на вторую ноду.
* `panel_upsert_subscription_template` (`1789-1831`) по имени `XRAY standard usa1` перезаписывает
  шаблон первой ноды.
* `panel_node_tag` (`1220-1231`) даёт обеим нодам `USA1`; скрытые хосты обеих нод попадают
  в один `injectHosts`-селектор, и подписки смешивают хосты.

**Влияние.** Вторая установка может «увести» существующую ноду с её профилем и хостами,
сломать подписки и выдать пользователям чужие/недоступные хосты. Это не гипотетика:
multi-node заявлен в README/коммите, а ручной режим с дефолтным `PREFIX` — документированный путь.

**Что сделать.**
1. Сделать стабильный per-node идентификатор (`NODE_TAG`/IP) частью имён:
   `node-<tag>`, `multi-<tag>-<domain>`, `XRAY standard <tag>`, remark `"VLESS Vision <tag>"`.
2. В `panel_find_node_by_address` матчить **только address**; совпадение по имени при другом
   address должно быть конфликтом с понятной ошибкой, а не PATCH.
3. В `panel_find_host_by_remark` искать по стабильному remark + inbound/profile UUID.
4. Добавить тест: две ноды с одинаковым `PREFIX`/доменом, разные `SERVER_IP` → в панели
   две ноды, два профиля, два набора хостов, теги не пересекаются.

### A-2. API-токен панели может уйти по HTTP

`normalize_panel_url` (`598-621`) **намеренно принимает** `http://`; это закреплено тестом
`tests/installer-funcs-checks.sh:425-426` («http с IP и портом должен сохраняться»).
`panel_api` (`2330-2334`) собирает `http://panel/api/...`, а `panel_curl_cfg_init`
(`2264-2275`) кладёт `Authorization: Bearer <token>` в curl-config. `curl` не следует
редиректам (нет `-L`), поэтому токен уходит в открытом виде ещё до возможного 301/308.

**Влияние.** Токен панели (по README его проще всего выдать как `*`) может быть перехвачен
в сети. `SECURITY.md` прямо относит утечку токена к ошибкам безопасности.

**Что сделать.** Требовать `https://` для публичных хостов. `http://` разрешать только для
loopback/приватных адресов и с явным предупреждением (или отдельным флагом). Добавить тест
на отказ `http://panel.example.com`.

### A-3. Go `1.26.9` отстал от security-релиза `1.26.10`

`GO_VERSION="1.26.9"` (`95`) и SHA256 (`317-322`) закрепляют патч, вышедший до
`go1.26.10` (2026-10-19, security-исправления `crypto/x509`). Caddy на этой сборке
терминирует публичный TLS `:443`.

**Что сделать.** Обновить как минимум до `1.26.10` (или `1.27.3`, если проверить сборку
Caddy/caddy-l4) и заменить SHA256:

```text
go1.26.10.linux-amd64.tar.gz  ccfe7ae822d2c2f41f4fe7c956199967a4dac22d0ee0d2b2bfdb440aab3b20c5
go1.26.10.linux-arm64.tar.gz  3f4227ce7b206a513e794f1393adb473a07b46e94d18bd15d1c684bbb7319797
```

Обновить `README.md:505` и прогнать CI. Добавить в guard проверку «версия Go не старше
последнего патча выбранной линии» (или хотя бы ручной чек-лист при обновлении).

## 4. P2 — исправить в следующем цикле

### A-4. `panel_api_success`: ложные успехи и ложные ошибки

Строка `2371`:

```bash
jq -e '.response != null or .success == true or .data != null or has("response") or has("data")'
```

`has("response")` делает успехом `{"response":null,"message":"boom"}`. Проверено:

```text
SUCCESS {"response":null,"message":"boom"}
SUCCESS {"response":null}
SUCCESS {"data":null}
```

Обратная проблема: 202/204 с пустым телом (реальный Remnawave 3.x для
`POST /nodes/{uuid}/actions/restart`, см. контракт `restart.command.d.ts` — ответа нет)
считается ошибкой. `panel_trigger_node_start` (`1610-1627`) вызывает
`panel_api_retry` (`2485-2509`), тот видит 202, не считает 4xx и **повторяет POST три раза**
с паузами 5 и 10 секунд. Итог: до трёх restart-событий и ложные warning'и.

**Что сделать.** Успех — это 2xx **и** (`.response != null` / `.success == true` /
`.data != null`) **без** `.errors`; `has()` убрать. Для action-эндпоинтов с 202/204 сделать
отдельную проверку («2xx и пустое тело — успех, не ретраить»). Добавить в мок 202 с пустым
телом и 200 `{"response":null,"message":"…"}`.

### A-5. REALITY privateKey в файле 0644

`write_config_profile` генерирует X25519 privateKey/shortIds (`1093-1116`) и сохраняет
`$NODE_DIR/Multiselect.json` через `install -m 644` (`1117`). Каталог `/opt/remnanode`
создаётся с обычным umask (0755), поэтому любой локальный пользователь может прочитать
приватные ключи REALITY. Кроме финального файла, промежуточные `$out.tmp`/`$out.tmp2`
создаются обычным redirection (umask 022 → 0644) и тоже содержат ключи, пока идёт запись.
Это противоречит `SECURITY.md` (утечка ключей — ошибка) и тому, что `.env` и лог уже 0600.

**Что сделать.** Писать профиль с `install -m 600` (или 640 root:root), создавать
временные файлы с `umask 077`/`mktemp` и добавить `chmod 600` на случай уже существующего
файла; тест на режим.

### A-6. `--api-token` светит токен в argv

Флаг `--api-token` (`128, 194-197`) кладёт секрет в командную строку. `/proc/<pid>/cmdline`
читается другими пользователями, токен остаётся в истории shell. Это противоречит
аккуратной работе с токеном через `-K`/`0600`.

**Что сделать.** Удалить флаг или оставить только для интерактивного ввода (не argv);
читать токен из env/stdin. В README — явно не рекомендовать этот флаг.

### A-7. Internal Squad выбирается «первым», а не по смыслу

`panel_upsert_internal_squad` (`1688-1693`) берёт `.[0]` из списка отрядов и добавляет
inbound'ы туда. Если в панели есть несколько отрядов (например, платный первым), нода
попадёт не в тот, а в чужой; пользователи другого отряда получат/потеряют доступ.

**Что сделать.** Искать `Default-Squad` по имени; если его нет — создавать отдельный
`Squad-<NODE_TAG>`; при неоднозначности — предупреждать и не трогать чужие отряды.
Тест: два отряда, проверка, что изменён нужный.

### A-8. Config Profile пишется до установки `openssl`

`write_config_profile` вызывается на `3292`, а `openssl` ставится только на шаге 3
(`3384-3389`). Генерация ключей выполняется только при `have openssl` (`1093`). На
минимальной Debian/Ubuntu без openssl:

* локальный `Multiselect.json` остаётся с пустыми `privateKey`/`shortIds`;
* в ручном режиме пользователь загружает его в панель → Xray не поднимает inbound'ы;
* в авто-режиме `panel_prepare_profile_for_api` позже сгенерирует ключи для панели, но
  локальный файл так и останется пустым/рассинхронизированным.

Плюс установка базовых пакетов на шаге 0 (`2642-2645`) только предупреждает при сбое:
если `jq` не встал, профиль не сохранится, а шаг 3 позже поставит `jq`, но `write_config_profile`
уже не перезапустится.

**Что сделать.** Добавить `openssl` в пакеты шага 0 или перенести `write_config_profile`/
`write_xray_template` после шага 3; сделать установку обязательных пакетов шага 0 фатальной
(или повторять запись профиля после шага 3). Тест: запуск с `PATH` без openssl/jq.

### A-9. `NODE_IMAGE`: `latest`, не сохраняется, README отстал

* дефолт — `remnawave/node:latest` (`52`), а `latest` на Docker Hub сейчас `3.4.4`;
* README заявляет проверенными `Node 3.0.0–3.1.1` (`25`) и советует пин `3.1.1`
  (`140`, `595`) — это уже не текущий `latest`;
* `NODE_IMAGE` не пишется в `ENV_STORE` (в отличие от остальных выборов). Если один раз
  запустить с `--node-image remnawave/node:3.1.1`, повторный запуск без флага снова возьмёт
  `latest` и перезапишет `.env`.

**Что сделать.** Сохранять `NODE_IMAGE` в `ENV_STORE` (или читать из `$NODE_DIR/.env`);
зафиксировать проверенный тег/дайджест в README и обновить матрицу совместимости после
теста с `3.4.x`; добавить тест на сохранение образа.

### A-10. Ротация Cloudflare-токена не обновляет acme.sh

`issue_cert_dns` (`3644-3667`) при валидном сертификате (>7 дней) делает `return 0` до
вызова `acme.sh`, поэтому новый `CF_Token` не попадает в конфиг сертификата. acme.sh
продолжит продление старым токеном и в какой-то момент молча не продлит CDN-сертификат.
README (`429`) при этом советует «перезапустите установщик для перевыпуска» — это не так.

**Что сделать.** При смене токена обновлять креды acme.sh (`acme.sh`-конфиг/аккаунт) или
делать `--issue --force` для DNS-сертификата; либо хранить хэш токена и перевыпускать при
изменении. Исправить README.

### A-11. Старые хосты остаются в подписке при смене хоста/префикса

Remark'ы хостов строятся из `host_label` (`1990-2043`), а `host_label` — это `PREFIX`
(ручной режим) или первый label `VLESS_HOST` (CF). `panel_find_host_by_remark` (`1491-1501`)
ищет по remark. Если префикс/хост изменился, создаются новые хосты, а старые остаются.
`NODE_TAG` при этом сохраняется, поэтому старые скрытые хосты с тем же тегом продолжают
попадать в `injectHosts` новой подписки. README (`110`) обещает «не дублируя … хосты» —
для смены хоста это неверно.

**Что сделать.** Использовать стабильный remark на основе `NODE_TAG` (и inbound UUID),
а не изменяемого host label; либо удалять/переиспользовать управляемые хосты по тегу+inbound.
Тест: смена `PREFIX` при повторном запуске не плодит хосты.

### A-12. `GET`-запросы панели без retry

`panel_find_profile_by_name` (`1449`), `panel_get_inbounds` (`1462`),
`panel_find_node_by_address` (`1476`), `panel_find_host_by_remark` (`1493`),
`panel_find_subscription_template_uuid` (`1773`) используют обычный `panel_api`. При
транзиентном 5xx/сетевом сбое список пуст → код делает `POST` (и получает 409) или не
обновляет существующий объект. `panel_api_retry` есть только у записей.

**Что сделать.** Использовать `panel_api_retry GET` для чтений (или отдельный
идемпотентный retry), добавить тесты на 5xx при чтении.

### A-13. `MULTISELECT_TEMPLATE_URL` не требует HTTPS

`MULTISELECT_TEMPLATE_URL` (`86`) скачивается в `write_config_profile` (`1050`), и
`existing_reality`/`panel_prepare_profile_for_api` **сохраняют непустые** `privateKey`
из шаблона (`1063-1075`). Если пользователь переопределит URL на `http://`, MITM может
подсунуть профиль с известными ему ключами REALITY. По умолчанию URL https, но проверки нет.

**Что сделать.** Требовать `https://` (или локальный файл) для `MULTISELECT_TEMPLATE_URL`;
то же для `SELF_STEAL_RAW_BASE`, когда он используется для конфига. Добавить тест.

## 5. P3 — hardening, надёжность, документация

### 5.1. Файлы и секреты

* **A-14. `ENV_STORE` без явного chmod.** `( umask 077; … ) > "$ENV_STORE"` (`3233-3282`)
  создаёт новый файл 0600, но **не меняет** права уже существующего. Если файл когда-то
  создан с 0644 (руками/старой версией/копированием), токены останутся читаемыми. `/root`
  обычно 700, поэтому риск условный, но `SECURITY.md` считает неверные права ошибкой.
  Добавить `chmod 600 "$ENV_STORE"` и тест.
* **A-15. `CERT_DIR` в Caddyfile без кавычек.** `tls $CERT_DIR/...` (`3782`, `3820`)
  ломается на пробелах; перевод строки/`}` в `CERT_DIR` — потенциальная инъекция в конфиг.
  Валидировать путь (абсолютный, без пробелов/переводов строк/фигурных скобок) или
  использовать безопасное представление.
* **A-16. CF-токен в curl-config без очистки.** `cf_curl_cfg_init` (`703`) печатает токен
  как есть; `panel_curl_cfg_init` (`2268`) хотя бы убирает whitespace. Токен с переводом
  строки/кавычкой ломает конфиг, а в худшем случае добавляет директивы curl. Чистить
  whitespace/кавычки и проверять формат.
* **A-17. `normalize_panel_url`.** Принимает `http://` (см. A-2) и `:99999`/пустой порт;
  не проверяет диапазон. Добавить проверку порта и регистронезависимую схему.
* **A-18. Невалидный `SERVER_IP`.** Если `SERVER_IP` задан, но не IPv4 (опечатка, IPv6),
  блок `2687-2710` не заменяет его автодетектом и не отвергает; далее он попадает в
  env-файл/сводку, а DNS-проверка сравнивает с мусором. Добавить `is_ipv4 || SERVER_IP=""`
  с предупреждением.
* **A-19. `--ssh-port`.** Проверяется только `^[0-9]+$` (`169-172`); `0`, `99999`, `-1`
  (последнее отсекается regex) пропускаются. Добавить 1–65535.

### 5.2. Зависимости и hardening

* **A-20. `ss`/iproute2.** `ss` используется в `assert_port443_free`, проверке :80 и шаге 10,
  но в списках пакетов его нет (`2644`, `3384-3389`). На минимальном образе шаг 10 упадёт
  с невнятной диагностикой. Добавить `iproute2` (или `have ss || die`).
* **A-21. Caddy admin API.** В генерируемом Caddyfile нет `admin off` (`3756-3772`).
  По умолчанию Caddy слушает `localhost:2019` без аутентификации; локальный пользователь
  может переконфигурировать Caddy (в т.ч. отдать файлы, доступные пользователю `caddy`).
  Если включать `admin off`, не забыть заменить `systemctl reload caddy` на restart для
  применения сертификатов.
* **A-22. Внешние источники.** `curl | sh` для Docker (`3393`) и acme.sh (`3564`), а также
  скачивание Caddy в CI (`tests/caddy-http-checks.sh:99-104`) без пина/суммы. Docker/acme.sh
  осознанно оставлены upstream (A-8 прошлого аудита), но для CI-бинаря Caddy стоит
  проверять SHA256 или кэшировать. `acme.sh --upgrade --auto-upgrade` запускает свежий код
  от upstream при каждом прогоне — задокументировать риск.

### 5.3. Документация

* **A-23. Расхождения README/usage/кода:**
  * `usage()` и меню говорят «5 вопросов», а быстрый режим задаёт 6 (плюс финальный
    `confirm`): `remnanode-setup.sh:27, 129, 152, 2674, 2724`; README уже говорит «6 вводов»
    (`65`). Привести к одному числу.
  * В авто-разделе README всё ещё «Tag USA» (`110`), хотя код использует `NODE_TAG`;
    в диагностике (`557`) — тоже.
  * README (`197`) утверждает, что `privateKey`, `shortIds`, `clients` «оставляет панель».
    На самом деле установщик генерирует ключи сам (`1093-1116`), а панель с пустым
    `privateKey` не поднимет REALITY. Для ручного режима это прямо вводит в заблуждение.
  * README (`25`, `140`, `505`, `595`) заявляет проверенными Node `3.1.1` / Xray `26.7.28`
    и Go `1.26.9`, хотя `latest` уже `3.4.4`, а Go-патч `1.26.10`. Обновить после теста.
  * README (`429`) неверно описывает перевыпуск после смены CF-токена (см. A-10).
  * `--node-tag` (`186-189`) и `NODE_TAG` не описаны ни в `usage()`, ни в README.
  * `Zone:Zone:Read` (`42`, `168`, `458`) — лишнее `Zone:`; правильное право `Zone:Read`.
  * `STEP_TOTAL=10` при шагах 0–10 (11 шагов); косметика.
  * `README` «Внешние источники» (`538`) в колонке «как зафиксировать» для acme.sh пишет
    `--upgrade --auto-upgrade`, то есть не пин.
* **A-24. Устаревшие аудит-документы.** `AUDIT.md` описывает `c7ea750` и «красный CI»;
  `AUDIT_FIX_PLAN.md` — состояние 2026-10-19 и прямо говорит «поддержка нескольких нод — не
  делаем», хотя multi-node уже в `main`. Пометить их историческими или обновить.
  `SECURITY.md` (`33`) называет `NODE_IMAGE` пином, но дефолт — `latest`.
* **A-25. Структура.** 4249 строк в одном файле, 55+ grep-инвариантов, тесты извлекают
  функции через `sed -n '/^fn() {$/,/^}$/p'`. Это работает, но хрупко: переименование/
  форматирование ломает тесты, а логика панели/Cloudflare/Caddy не изолирована. Нет
  `--uninstall`/`--dry-run`. Для дальнейшего роста стоит вынести модули (`panel.sh`,
  `caddy.sh`, `cloudflare.sh`) и добавить smoke-тест полного сценария на моке.

### 5.4. Прочее

* **A-26. RSA-сертификат и `--ecc`.** `issue_cert` (`3614-3624`) пропускает выпуск, если
  сертификат валиден >7 дней, а `--install-cert` (`3679-3688`) всегда использует `--ecc`.
  Если в `~/.acme.sh` лежит старый RSA-сертификат, установка упадёт. Проверять тип
  сертификата или использовать `--force`/правильный install.
* **A-27. Ложный успех авто-настройки и 409 ноды.** При пустом списке inbound'ов
  `panel_auto_setup` (`1949-1979, 2068-2077`) может вернуть 0 с «хостов=0», хотя нода не
  создана. `panel_upsert_node` при 409 не переискивает ноду (в отличие от profile/host).
  Считать отсутствие inbound'ов ошибкой; обрабатывать 409 повторным поиском.
* **A-28. GitHub-гигиена.** `has_issues=false`, нет тегов/релизов/CHANGELOG. Для установщика
  от root стоит включить Issues/приватные security advisories и выпускать версии/теги,
  чтобы пользователь мог ссылаться на проверенную ревизию.

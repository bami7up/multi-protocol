# Аудит проекта multi-protocol

**Ревизия:** `c7ea750` (`main`) · **Дата:** 2026-10-16 · **Ветка аудита:** `arena/5fb400e2-multi-protocol`

Предмет: установщик ноды Remnawave с четырьмя протоколами (VLESS Reality/Vision + self-steal, VLESS XHTTP,
Hysteria2, VLESS за CDN), шаблоны Config Profile/XRAY_JSON, темы фасада, тесты и CI.

**Итог в одном абзаце.** Архитектура продумана, документация подробная и в целом совпадает с кодом, а
проверок в CI больше, чем обычно бывает в подобных репозиториях (shellcheck, юнит-тесты с моками API,
валидация JSON5, интеграционный тест на настоящем Caddy, 40 grep-инвариантов). Но **CI на `main` красный**:
падает именно интеграционный тест Caddy-слоя, а вместе с ним не выполняются все защитные шаги после него.
Причина — не в продакшн-конфигурации, а в самом тесте: мок gRPC-апстрима собран так, что не может ответить
по h2c. Исправление внесено и проверено на настоящем Caddy. Кроме этого найдены три дефекта повторного
запуска установщика (в том числе **молчаливое отключение CDN**), неработающий документированный обходной
путь для NAT (`SERVER_IP`), устаревший Go-тулчейн в сборке Caddy и набор вопросов по процессам (лицензия,
отключённые Issues, непинованные внешние источники).

## 3. Находки

### A-1 (P0). CI красный: падает проверка gRPC/h2c, остальные защитные проверки не выполняются

**Что происходит.** На `main` красные два последних прогона (`38874924999` от коммита про CDN и
`38875996699` от коммита про README). Падает шаг «Integration-test the generated Caddyfile on a real Caddy»,
все шаги после него (whitespace, «Guard fixed invariants») пропускаются:

```
✔ CDN-путь /probe/ws маршрутизируется в Xray (апстрим недоступен → 502)
✔ CDN-путь /probe/xhttp маршрутизируется в Xray (апстрим недоступен → 502)
✖ gRPC-путь: ожидался ответ h2c-апстрима (200), получено 502
```

Это воспроизведено локально на настоящем Caddy с layer4 — то есть сборка логики теста воспроизводима, и
причина воспроизводится детерминированно.

**Причина.** Дефект самого теста, а не продакшн-конфигурации. Мок h2c-апстрима в `tests/caddy-http-checks.sh`
(до правки) выглядел так:

```caddyfile
{
  auto_https off
  servers {
    protocols h2c
  }
}
127.0.0.1:$CDN_GRPC_PORT {
  respond "grpc-h2c-upstream"
}
```

Три независимых дефекта мока, каждый из которых проверен отдельно на живом Caddy:

1. **Нет схемы `http://`.** `auto_https off` отключает автоматический выпуск сертификатов, но не делает сайт
   cleartext-овым: адрес без схемы считается HTTPS-адресом, и Caddy добавляет `tls_connection_policies: [{}]`
   (`caddy adapt` это показывает). Апстрим начинает говорить TLS, поэтому проксирование по h2c даёт 502.
   Проверка: `curl --http2-prior-knowledge http://127.0.0.1:PORT/` → обрыв; при схеме `http://` → `200`.
2. **`protocols h2c` без `h1`.** Caddy документирует требование: «If enabling `h2` or `h2c`, `h1` must also be
   enabled» (ограничение стандартной библиотеки Go). С `protocols h2c` запрос по HTTP/1.1 получает
   `Connection reset`, с `protocols h1 h2c` работают оба протокола.
3. **Host-матчер в адресе сайта.** Даже после добавления `http://`, адрес `http://127.0.0.1:PORT` создаёт
   matcher по Host. `reverse_proxy` сохраняет клиентский Host (`cdn.test.local:19443`), поэтому ни один route
   не совпадает и апстрим отвечает **пустым 200** (в access-логе апстрима — `"msg": "NOP"`, `status: 0`,
   `bytes_read: 0`). Именно эту ситуацию тест и видел как «до h2c-апстрима дошёл не тот запрос».

**Влияние.** Формально красный CI блокирует мержи и обесценивает значок сборки; по существу — **цепочка
CDN → origin → Xray по gRPC/h2c никогда не проверялась**, хотя README утверждает обратное. При этом мок
маскировал реальные ошибки конфигурации: например, «правильный» вывод теста достигался бы и при сломанном
h2c-маршруте.

**Исправление (внесено).** В моке: `admin off`, `protocols h1 h2c`, адрес `http://:$CDN_GRPC_PORT` (без хоста),
поясняющий комментарий с разбором всех четырёх деталей. Продакшн-часть (`reverse_proxy ... h2c://127.0.0.1:10448`
в генерируемом Caddyfile) не менялась — она корректна, что и подтверждает прогон:

```
✔ CDN-путь /probe/grpc/Tun проксируется в Xray по h2c (ответ апстрима получен)
✔ tls1_2 согласован (Protocol version: TLSv1.2) / ✔ tls1_3 согласован
✔ TLS 1.0 и 1.1 не согласуются
все проверки HTTP-слоя Caddyfile прошли
```

**Дополнительная рекомендация.** CI проверяет тест на Caddy `v2.11.4` из GitHub Releases — это сеть в
критическом пути сборки. Полезно кэшировать бинарник (`actions/cache`) или использовать матрицу версий.

### A-2 (P1). Повторный запуск молча выключает CDN

**Что происходит.** Установщик сохраняет ответы в `/root/remnanode.env`, и в нём CDN записан как число:

```bash
# remnanode-setup.sh:1103
printf 'export ENABLE_CDN=1\n'
```

При повторном запуске этот файл подхватывается (`source "$ENV_STORE"`), после чего флаг разбирается так:

```bash
# remnanode-setup.sh:954
ask ENABLE_CDN "Добавить VLESS за CDN (Cloudflare и др.)?" "${ENABLE_CDN:-n}"
if [[ "${ENABLE_CDN,,}" != y* ]]; then   # "1" не начинается с "y"
  ENABLE_CDN=0
```

Проверено на извлечённом фрагменте установщика с реальными значениями:

```
ENABLE_CDN=1 (env-файл установщика)   ENABLE_CDN=0
ENABLE_CDN=y (README / первый запуск) ENABLE_CDN=1
ENABLE_CDN=n (явное выключение)       ENABLE_CDN=0
ENABLE_CDN пусто (дефолт)             ENABLE_CDN=0
```

**Влияние.** При повторном запуске (в том числе `--non-interactive`, который печатает ответы как «статусы»):

* из `/etc/caddy/Caddyfile` исчезают L4-маршрут CDN-хоста и CDN-сайт `https://<CDN_HOST>:9444`;
* из `$NODE_DIR/Multiselect.json` вырезаются CDN-инбаунды — сохранённый профиль перезаписывается;
* сертификат CDN-хоста и проксируемая A-запись в Cloudflare остаются.

Итог: CDN-хост перестаёт работать (CDN в режиме Full (strict) получает чужой сертификат), а пользователь
узнаёт об этом только по жалобам клиентов. Это противоречит README: «запоминать ответы не нужно… повторный
запуск задаёт те же вопросы с готовыми значениями» и разделу «Повторный запуск и безопасность».

**Рекомендация.** Нормализовать разбор флага (и писать в env-файл уже нормализованное `y`/`n`):

```bash
case "${ENABLE_CDN,,}" in
  y|yes|1|true|on) ENABLE_CDN=1 ;;
  *)               ENABLE_CDN=0 ;;
esac
# и в env-файл:
printf 'export ENABLE_CDN=%s\n' "$([[ $ENABLE_CDN == 1 ]] && echo y || echo n)"
```

Дополнительно стоит закрыть это CI-инвариантом (см. A-6), иначе регресс вернётся.

### A-3 (P1). Числовые значения флагов трактуются как «выключено»

**Что происходит.** Оба флага сравниваются с `y*`, поэтому любые «истинные» значения, кроме `y*`, означают
«нет». Для `ENABLE_XHTTP` это неочевидно вдвойне: `usage()` и README предлагают `ENABLE_XHTTP` как
переменную для `--non-interactive`, а интуитивное значение `1` даёт противоположный результат:

```
ENABLE_XHTTP=1 → 0 (XHTTP выключен, SNI/path вычищаются)
ENABLE_XHTTP=y → 1
ENABLE_XHTTP=0 → 0
```

**Влияние.** Пользователь, задавший `ENABLE_XHTTP=1` (как и `ENABLE_CDN=1`), получает конфигурацию,
противоположную намерению, при этом установщик только предупреждает «XHTTP в selfsteal отключён».
Для CDN это описано в A-2, здесь — тот же дефект на второй ветке.

**Рекомендация.** Единая нормализация булевых env-переменных (функция `parse_bool`) для `ENABLE_XHTTP`,
`ENABLE_CDN` и `ASSUME_YES`/`NONINTERACTIVE`; в `usage()` явно указать допустимые значения (`y|n|1|0|yes|no`).

### A-4 (P2). `SERVER_IP` из окружения игнорируется

**Что происходит.** Переменная обнуляется перед автодетектом:

```bash
# remnanode-setup.sh:898
SERVER_IP=""
if have curl; then
  SERVER_IP="$(curl -4 -sS --max-time 10 https://ifconfig.me ...)"
```

Все остальные переменные подхватываются из env (`${VAR:-}`), эта — нет. При этом:

* README (`README.md:486`) советует: «при необходимости переопределите `SERVER_IP` (например, если нода за NAT
  и определить публичный адрес не удалось)»;
* сообщение об ошибке установщика (`remnanode-setup.sh:461`) советует «Задайте `SERVER_IP` через env»;
* в `usage()` `SERVER_IP` вообще отсутствует.

**Влияние.** На сервере за NAT/CGNAT или без доступа к `ifconfig.me`/`api.ipify.org` режим Cloudflare
невозможен: установщик падает с рекомендацией, выполнить которую нельзя. Дополнительно: определение
публичного IP через сторонний сервис по HTTPS — лишняя зависимость (в README не задокументирована).

**Рекомендация.**

```bash
if [[ -n "${SERVER_IP:-}" ]] && is_ipv4 "$SERVER_IP"; then
  ok "Публичный IPv4 (из env): $SERVER_IP"
else
  SERVER_IP=""   # и только затем автодетект
fi
```

и добавить `SERVER_IP` в `usage()`; в идеале — определять адрес через `ip -4 addr`, а внешний сервис
использовать лишь как fallback.

### A-5 (P2). Порт ноды может совпасть с портом CDN-схемы

**Что происходит.** Запрещённые значения `NODE_API_PORT` перечислены вручную и не покрывают порты CDN-режима:

```bash
# remnanode-setup.sh:1004
case "$NODE_API_PORT" in
  80|443|9443|10443|10444) die "Node API port $NODE_API_PORT занят этой схемой..." ;;
esac
```

Порты `9444` (CDN-сайт Caddy), `10446`–`10448` (CDN-инбаунды Xray) в список не входят.

**Влияние.** При `ENABLE_CDN=y` и, например, `NODE_API_PORT=10446` Xray не сможет занять порт инбаунда
(порт занят контейнером ноды), нода уйдёт в `Offline`, а диагностика укажет на «не поднялись инбаунды» —
без указания на конфликт портов. При `NODE_API_PORT=9444` ломается CDN-сайт.

**Рекомендация.** Дополнить список до `9444|10446|10447|10448` и/или строить его из активных портов схемы
(`CDN_TLS_PORT`, `CDN_*_PORT`) с учётом `ENABLE_CDN`.

### A-6 (P2). Тесты не покрывают разбор env-флагов и идемпотентность

**Что происходит.** Юнит-тесты (`tests/installer-funcs-checks.sh`) покрывают валидаторы, генератор хостов,
Cloudflare-оркестрацию, фильтр профиля и фрагменты Caddyfile, но не покрывают «шаг 1» — разбор ответов и
переменных окружения. Из-за этого P1-дефекты A-2/A-3 прошли и CI, и ревью.

**Рекомендация.** Извлекать фрагменты разбора (`ask ENABLE_XHTTP` … `fi`, `ask ENABLE_CDN` … `fi`) тем же
приёмом, что уже используется для `XHTTP_L4_BLOCK`/`CDN_L4_BLOCK`, и проверять таблицу значений
(`y`, `Y`, `yes`, `1`, `0`, `n`, пусто, `ENABLE_CDN=1` из env-файла). Дополнительно — инвариант в
`validate.yml`: значение, которое установщик пишет в `ENV_STORE`, обязано включать CDN при повторном запуске.

### A-7 (P2). Устаревший Go-тулчейн в сборке Caddy

**Что происходит.** `GO_VERSION="1.25.1"` (релиз 2025-09-03) с проверкой SHA256 — механизм правильный,
хеши совпадают с официальными (см. раздел 5), но версия сильно отстала: в линии `1.25` уже вышли
`1.25.2` … `1.25.14` (последний — 2026-08-19), а также `1.26.x` и `1.27.x`. Требование обоих проектов —
лишь минимум: `caddy-l4 v0.1.2` → `go 1.25.1`, `caddy v2.11.4` → `go 1.25.1`.

**Влияние.** Собранный бинарник Caddy несёт стандартную библиотеку Go образца сентября 2025 года; в патч-релизах
Go традиционно закрываются уязвимости stdlib (net/http, crypto/tls и т.п.). Caddy слушает публичные `80/443`.

**Рекомендация.** Поднять `GO_VERSION` до последней `1.25.x` (или до текущей поддерживаемой линии) и обновить
оба `go_sha`. Хеши удобно брать из `docker-library/golang` (`1.25/<дистрибутив>/Dockerfile`) или
`https://go.dev/dl/?mode=json`. Заодно стоит добавить комментарий с датой проверки хешей — сейчас в коде
непонятно, когда они сверялись.

### A-9 (P2). Origin CDN-хоста достижим напрямую

**Что происходит.** L4-маршрут выбирает получателя по SNI, поэтому `SNI=CDN_HOST` на `443/tcp` ноды приводит к
CDN-сайту Caddy, а пути транспортов — к инбаундам Xray:

```
curl --resolve cdn.example.com:443:<IP ноды> https://cdn.example.com/api/v1/stream
```

Это ожидаемое поведение схемы (аутентификация остаётся за VLESS-UUID), но означает, что «скрытие IP ноды»
держится только на том, что посторонний не знает origin-IP и SNI — активное сканирование адресного
пространства с `SNI=cdn.example.com` находит origin. Формально это скорее ограничение дизайна CDN-прокси,
но в README раздел описывает именно сокрытие origin как преимущество.

**Рекомендация.** Либо явно описать ограничение в README, либо добавить защиту origin:

* Cloudflare Authenticated Origin Pulls (mTLS) — Caddy проверяет клиентский сертификат Cloudflare;
* либо требование секретного заголовка/`Host`-проверки на CDN-сайте (плюс запрет прямого доступа к CDN-SNI
  извне, кроме адресов CDN — на практике неудобно из-за смены диапазонов Cloudflare).

### A-13 (P3). `apt_wait` полагается на неустановленный `fuser`

`apt_wait()` (`remnanode-setup.sh:695`) вызывает `fuser`, который приходит с пакетом `psmisc`, а `psmisc`
ставится только на шаге 3 (`:1198`). Первый вызов `apt_get` происходит на шаге 0. На минимальном образе без
`psmisc` все проверки блокировки молча дают `command not found` (вывод перенаправлен в `/dev/null`), и ожидание
освобождения `dpkg`-locks не работает. Рекомендация: проверять `have fuser` (и предупреждать), либо ставить
`psmisc` в самом начале, либо использовать `flock`-совместимую проверку.
